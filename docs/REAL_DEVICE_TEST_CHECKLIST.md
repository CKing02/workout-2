  `setProgressTintList` 只是**运行时更新**通道受限，而进度条在**我们自己的 layout**
  里（`modules/.../res/layout/notification_rest_timer.xml`），layout 属性是
  inflate 时解析的，不受该 API 限制 —— 加 `android:progressTint`（API 21+ 属性）

#### 13.1 G31 plan_sets 处方回滚缺口 → 已修（2026-10-01，代码 + 单测；**真机未复验**）

- **症状**：导出计划（G24a 设过 60kg×10）→ G14 清除 → G31 导入同一文件 →
  计划的组数 / 动作骨架还在，但 **weight / reps / setType 全变回默认**，
  `plan_exercises.rest_seconds` 也被抹成 **60**。全程无任何报错。
- **真根因**（比条目最初写的更重 —— 最初定性为「导出端没带 → 导入端不写」，
  实际是**导入端主动删除**，属净破坏）：

  | 位置 | 代码 |
  |---|---|
  | `importData.ts` 清表段 | `DELETE FROM plan_sets;` |
  | `importData.ts` plan_exercises INSERT | `VALUES (?, ?, ?, ?, 60)` —— **rest_seconds 硬编码 60** |
  | `exportData.ts` `BackupPayload` | 只 `SELECT plan_id, exercise_id, position`，`rest_seconds` / `plan_sets` 压根没导 |

- **修法（v2 payload）**：把 sets **内嵌**进 `planExercises` 条目 ——
  `{planId, exerciseId, position, restSeconds, sets:[{setIndex, setType, weight, reps, durationSeconds, distanceKm}]}`
  - 为什么不用「旧 id → 新 id」映射表：`plan_exercises.id` 导入时是 `newId()`
    **重新生成**的，而 `plan_sets.plan_exercise_id` 指向它、payload 里又没带。
    内嵌之后导入端拿着刚生成的 UUID **立刻**写 sets —— 零映射、零查找。
  - 导出端 SQL 改成 `plan_exercises LEFT JOIN plan_sets`
    （`LEFT` 是为了「还没配过组」的 link 也仍出一行）。
  - `schemaVersion` **1 → 2**；导入端 **1 / 2 都接受**，v1 老备份缺
    `restSeconds` / `sets` 时降级成 60 / 空组，**不抛错**。
  - `ImportCounts` 增 `planSets`，如实报告还原了多少组。

#### 13.15 exercises 导入丢 G35 五字段 → 已修（2026-09-30，真机踩到）

> **这是本项目目前最贵的一个 bug**：静默、全量、且验收时擦肩而过。

- **症状**：动作库 / 训练页**所有 GIF 不显示**，详情页中文说明与步骤空白。
  看起来完全像「网络挂了 / CDN 挂了 / 缓存坏了」。
- **真根因**：`src/utils/importData.ts` 的 `INSERT INTO exercises` **只写 9 列**，
  而导出端 dump 的 `Exercise` 视图**带** G35 五字段
  （`description_zh` / `steps_zh` / `gif_url` / `target_zh` / `attribution`）。
  导出带了、导入不写；又因为导入开头就 `DELETE FROM exercises`，
  所以「导出 → 导入」是**净破坏**。
- **判据（关键，下次别再往网络方向查）**：
  `SELECT COUNT(*) FROM exercises WHERE gif_url IS NULL` →
  如果拿到的是**全量数字**（306/306）而不是零星几条，就该怀疑导入，不是网络。
  当天实测：`306 总 / 306 NULL`。
- **怎么发现的**：用户报「手机没加载 GIF」。CDN 直连 `curl` 返回
  `200 / 95KB / image/gif`（**CDN 完全正常**），设备 `cache/gifs` 压根不存在 →
  拉下设备 DB 才看到 `gif_url` 整列为 NULL。
- **反向证据链（证明是导入而非 seed）**：设备上那份 **18:09 导出的备份里
  306 条全都带 gifUrl**（52 `asset:` + 254 CDN https），而现在 DB 里全 NULL，
  且 `created_at` 仍是 18:05 —— 说明行是**被导入改写**的，不是重新 seed 的。
- **是谁触发的**：2026-09-30 验收 **45.10「导入备份 → 头像不受影响」那一跑**。
  那条 AC 本身**通过了**（头像确实没变），但同一次导入把 306 个 GIF 全清了 ——
  **验证只盯了头像、没回动作库，所以当场没发现**。

  必须覆盖**所有**受到影响的域，而不是只看本次改动的那一个域。
  45.10 只验头像 = 有判别力但**视野太窄**。
- **修法**：INSERT 补 5 列 + 5 个绑定（`steps_zh` 走 `JSON.stringify`，
  与 `schema.ts` 的 `rowToExercise` 反解对称）。
- **回归测试**：`src/utils/__tests__/importDataDbWrite.test.ts`，5 条，
  **已确认撤掉修复后 4/5 失败**（有判别力）。用假 db 记录 SQL + 绑定参数，
